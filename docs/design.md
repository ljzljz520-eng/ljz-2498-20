# 文稿平台·发布校对关口 设计文档

## 1. 目标与术语

在"保存 → 发布"之间设置一道**校对关口（Proofreading Gate）**：

- **保存（saved）**：正文/属性已落库，只代表"内容已保存"。
- **校对通过（gate-passed）**：某次扫描在**当前规则版**下无未豁免阻断问题，且其**依赖清单仍然有效**。
- **已发布（published）**：发布事务成功，存在一个不可变的**确定快照（snapshot）**和发布指针。

三种状态严格区分：校对通过**不自动**等于发布；旧的校对通过可能因正文之外的变化失效。

## 2. 校对四类问题（逐项可定位）

| 规则码 | 含义 | 定位信息 |
|---|---|---|
| `heading.skip` | 标题层级跳跃（如 H1 后直接 H3） | 行号、该级标题文本、期望层级 |
| `link.empty` | 空链接（`[文字]()`、`href=""`、纯锚点占位） | 行号、链接文字 |
| `comment.open` | 仍处于打开状态的批注 | 批注 ID、锚定文本、行号 |
| `asset.description` | 图片/资源缺少资源说明（alt/版权说明等） | 资源 ID、行号 |

每个问题生成稳定 **指纹 `fingerprint = sha256(ruleCode + 定位对象ID/行内序列 + 规范化文本)`**。
指纹用于与豁免精确匹配，而不是"同类错误"模糊匹配。

## 3. 依赖清单（Dependency Manifest）——核心设计

扫描结果是否仍有效，**不能比较文稿更新时间**。扫描时为每份通过报告生成依赖清单，逐项记录所依赖对象的**身份与版本**：

```
content_doc_rev   文稿正文修订号（body_rev，只在正文真正变化时递增）
heading[]         每个标题的 {行号, 层级, 文本hash}
link[]            每个链接的 {行号, 目标, 文字hash}
asset[]           引用资源的 {assetId, 状态版本 statusRev, 撤回标志 withdrawnRev}
comment[]         相关批注的 {commentId, 状态版本 statusRev, open标志}
permission        作者权限版本 permRev（含"作者"集合）
rule_version      生效规则版 ruleVersion
exemptions[]      被使用的豁免 {id, 版本, 绑定指纹}
```

### 失效判定（发布事务内逐项核对）

以下变化**正文未变**也会让旧通过失效：

1. **图片被撤回**：`asset.statusRev` 增长或 withdrawn 版本变化 → 即使 body_rev 不变，资源依赖失配。
2. **批注重新打开**：`comment.statusRev` 增长（resolved→open）→ 批注依赖失配。
3. **作者权限改变**：`permRev` 增长（作者移除/降权）→ 权限依赖失配。
4. 规则版升级、标题被改动、豁免被撤销/超出版本范围 → 对应依赖失配。

发布事务重新读取上述每一项并与清单比对；**任一项失配即拒绝发布**（要求重新扫描），错误信息精确指出"哪一项依赖变了"。

## 4. 豁免模型（不可继承）

豁免记录绑定四元组：

```
(documentId, ruleCode, fingerprint, valid_from_version, valid_to_version, reason)
```

- 限定**具体问题**：`ruleCode + fingerprint` 必须与扫描发现的问题完全一致。
- 限定**具体版本**：仅在文稿版本区间内有效。
- **新增同类错误不能继承旧理由**：不同位置/文本的问题指纹不同，自动匹配失败，必须重新申请。
- 规则版升级后旧豁免默认不适用新版本范围；撤销豁免立即生效。

## 5. 两种发布设计的比较与选择

### 方案 A：全部检查放进发布事务
- 做法：点击发布时开启事务，跑全部校验（含资源外链检查、批注、权限），通过则写快照。
- 缺点：
  - 资源检查可能很慢（外部资源服务迟到/超时），长事务持锁，并发发布互相阻塞。
  - 可解释性差：用户在点发布之前看不到完整问题清单，失败只得到一个拒绝。
  - 资源服务"迟到"期间事务无法收尾，易触发忙/超时。

### 方案 B：预检结果 + 发布时依赖校验（**选定，B+**）
- 做法：
  1. **扫描（可重复、可解释）**：`POST /api/documents/:id/scan` 同步跑本地校验，并对外部资源登记 `checking` 任务；全部资源确认后扫描报告转为 `passed`，返回逐项问题、定位、豁免命中和依赖清单。
  2. **发布（权威、原子）**：`POST /api/documents/:id/publish {scanId, idempotencyKey}` 在**单个 `BEGIN IMMEDIATE` 事务**内：
     - 锁定文稿行；若已发布过且指针快照相同 → 幂等返回（应对并发点击/任务重试）；
     - 重新读取依赖清单中每一项的当前版本，逐项比对（**不是重跑慢速外部检查，而是核对权威版本号**）；
     - 检查资源检查任务状态（迟到/失败 → 拒绝）；
     - 检查豁免在当前版本仍存在且匹配；
     - 全部成立 → 写入**不可变快照** `published_versions`（snapshot_json 含正文、规则版、依赖清单、通过的 scanId），更新文档发布指针，事务提交。
- 为什么不会读到"半套结果"：
  - `BEGIN IMMEDIATE` 立即取 SQLite 保留锁 + 写锁，并发发布请求第二个起即 `SQLITE_BUSY`（有界重试），不会有两个事务交错提交两份正式版；
  - 依赖核对与快照/指针写入在**同一事务**，任何一步失败整体回滚，外部永远看不到"指针已动、快照未写"的中间态；
  - 资源任务状态也在同一库里同事务读取，扫描与任务更新之间由行级现状保证一致。
- 可解释性：用户发布前看到逐项问题（标题层级/空链接/批注/资源说明）、每项定位、豁免理由；发布被拒时返回**具体失配依赖项**。

结论：选择 **B+（预检 + 事务内权威依赖复核）**，兼顾可解释性、低持锁与原子性。

## 6. 关系库表（SQLite，见 server/db.js）

`users`、`documents`（含 body_rev / perm_rev / published_version_id 指针）、`assets`（status_rev/withdrawn_rev）、
`comments`（status_rev/open）、`rule_versions`（规则版，仅一条 active）、
`scans`（报告状态）、`scan_issues`（逐项问题+定位+指纹+豁免命中）、
`exemptions`（规则码+指纹+版本区间）、`scan_dependencies`（依赖清单 JSON）、
`published_versions`（**不可变**快照，scan_id 唯一约束防双正式版）、
`asset_check_jobs`（资源校验任务/重试/迟到模拟）、`idempotency_keys`（任务重试去重）。

## 7. 并发与故障语义

- **并发点击发布**：同 scanId 的两个发布请求，唯一约束 + 即时锁 + 幂等键，保证只有一份正式快照，另一个返回同一份结果。
- **扫描后修改标题**：依赖清单 heading 版本失配 → 拒绝发布并指明标题项变化。
- **资源校验迟到**：扫描停留在 `checking`；发布事务读到任务未完成 → 拒绝（"资源校验尚未完成"）；迟到期间资源若被撤回，任务结果落地为 failed，同样拒绝。
- **任务重试**：所有写操作带幂等键；重试返回首次结果，不产生第二快照/重复副作用。
- **数据库中断**：事务提交前连接中断 → 无快照无指针（原子回滚）；客户端可安全重试（幂等）。
- 序列化冲突（SQLITE_BUSY）在服务层有界重试，不把半失败暴露给用户。

## 8. 界面三态

顶栏用三枚互斥状态徽标清晰区分：

1. **内容已保存**（灰色）：最近一次保存的修订号；
2. **校对通过**（蓝色）：通过的扫描号 + 规则版，附"依赖是否仍有效"的实时指示；
3. **已经发布**（绿色）：正式版本号 vN 与快照时间；正文修订号晚于快照版本时显示"有未发布改动"。

问题面板按四类分组、逐条显示行号与"定位"按钮（跳转正文行并高亮）；豁免显示理由与版本区间。
